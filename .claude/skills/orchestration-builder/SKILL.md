# orchestration-builder

Build the Kairos orchestration layer exactly as specified in [docs/technology-stack.md](../../../docs/technology-stack.md). This skill is the procedural companion to that document for *tying everything together*: the tech-stack doc decides *what* runs, this skill decides *how* the pieces are orchestrated, containerized, and launched as one stack. It is the integrator over its siblings — `backend-builder`, `frontend-builder`, `database-builder`, `observability-builder`, and `mcp-builder` each own a slice; this skill assembles them into a runnable whole.

**Read [docs/technology-stack.md](../../../docs/technology-stack.md) first** — it is the source of truth. [docs/report-technical-design-research.md](../../../docs/report-technical-design-research.md) holds the rationale (the dev/prod obs split, the `aspire publish`→Compose flow, why the dashboard is dev-only). If anything here conflicts with the tech-stack doc, the doc wins; update this skill to match.

## Canonical orchestration stack (from the tech-stack doc)

- **Dev orchestration:** **.NET Aspire AppHost** — service discovery, resource wiring, connection-string injection, OTLP endpoint injection, the dev dashboard. `aspire publish` emits the `docker-compose.yml` + `.env`; `aspire deploy` runs it **locally only** (it is *not* a remote-deploy tool — treat it as a CI step that emits a Compose artifact)
- **Shared defaults:** **`Kairos.ServiceDefaults`** — OTel, health checks, resilience, service discovery applied to every host
- **Containers:** **Docker** — every service is containerized (web, postgres, reverse proxy, observability stack). **MCP runs in the same process as `web`** (`/mcp`), so there is no separate MCP container or `mcp` resource
- **Local stack:** **Docker Compose, two files** — `compose.dev.yml` (full obs stack + Aspire Dashboard) and `compose.prod.yml` (app + Postgres + a pared-down OTel pipeline). A full obs stack can out-consume the app on one machine, so prod is deliberately minimal
- **Reverse proxy:** **Caddy or YARP** — terminates HTTPS on loopback so the browser sees HTTPS while the app speaks HTTP/2 cleartext (`h2c`) behind it. HTTP/3/QUIC is irrelevant on loopback — don't bother
- **Named volumes:** `kairos_pgdata` (Postgres), `dpkeys` (Data Protection keys for OAuth-token encryption), `kairos_files` (future attachments) — bind-mount under `%USERPROFILE%\KairosData\` on Windows for visibility

> **Guiding principle:** one contract, two runtimes. The **Aspire AppHost** is the source of truth for the resource graph and the inner-loop dev orchestrator; **Docker Compose** mirrors it (generated by `aspire publish`). Service names, ports, the `kairosdb` database name, and the OTLP endpoint must stay identical across both. Each service owns its own Dockerfile; this skill owns how they connect.

## What lives where

```
Kairos.sln
src/
  Kairos.AppHost/            # Aspire orchestrator — declares resources + references (dev inner loop)
  Kairos.ServiceDefaults/    # shared OTel/health/resilience/discovery (referenced by the web host)
  Kairos.Web/Dockerfile      # the single app host: Razor UI + /api/* + /mcp + GoogleCalendarSyncWorker
observability/               # collector/prometheus/loki/tempo/grafana configs (observability-builder)
reverse-proxy/               # Caddyfile (or YARP config) — HTTPS termination on loopback
compose.dev.yml              # full local stack: app + postgres + full obs + dashboard
compose.prod.yml             # single-user prod: app + postgres + minimal OTel-to-disk
.env                         # generated alongside compose by `aspire publish`
.dockerignore
```

## Build workflow

Get the Aspire AppHost running the full graph first (fastest feedback), then let `aspire publish` generate compose and tune the dev/prod split by hand. Run `dotnet build` after AppHost changes and `docker compose -f compose.<env>.yml config` to validate compose before `up`. Don't batch failures.

### 1. ServiceDefaults (shared host wiring)
Every executable host references `Kairos.ServiceDefaults` and calls `builder.AddServiceDefaults()` + `app.MapDefaultEndpoints()`. It centralizes:
- OpenTelemetry (delegated to `observability-builder`),
- **health checks** (`/health` liveness, `/alive` readiness),
- **HTTP resilience** (`AddStandardResilienceHandler`),
- **service discovery** for inter-service calls by logical name.

### 2. Aspire AppHost — the dev orchestrator (`Kairos.AppHost/AppHost.cs`)
Declare every resource and wire references so connection strings + endpoints are injected automatically. **Guard dev-only resources** (the observability stack, pgAdmin) with `builder.ExecutionContext.IsRunMode` so they never leak into the published prod compose:
```csharp
var builder = DistributedApplication.CreateBuilder(args);

// Data (database-builder owns the details). PG 17, persistent volume.
var postgres = builder.AddPostgres("postgres").WithDataVolume("kairos_pgdata");
if (builder.ExecutionContext.IsRunMode)
    postgres = postgres.WithPgAdmin();          // dev-only admin UI
var kairosdb = postgres.AddDatabase("kairosdb");

// The single app host: Razor UI + Minimal APIs (/api/*) + MCP (/mcp) + GoogleCalendarSyncWorker.
// Data Protection keys + OAuth tokens persist to the dpkeys volume.
var web = builder.AddProject<Projects.Kairos_Web>("web")
                 .WithReference(kairosdb).WaitFor(kairosdb)
                 .WithExternalHttpEndpoints();

// Dev-only: full observability stack as Aspire resources (observability-builder owns configs).
if (builder.ExecutionContext.IsRunMode)
{
    // builder.AddContainer("grafana", ...), prometheus, loki, tempo, otel-collector
}

builder.Build().Run();
```
Resource names (`postgres`, `kairosdb`, `web`) are **the contract** — they must match the `ConnectionStrings__kairosdb` keys used in `Kairos.Infrastructure` and the service names in both compose files. MCP is served at `/mcp` on `web`, so there is no separate `mcp` resource. The core domain aggregate is `TaskItem`.

### 3. Per-service Dockerfiles (multi-stage)
`Kairos.Web` owns its `Dockerfile`; this skill ensures it follows one pattern: restore → build → publish → slim runtime image.
- **`Kairos.Web`** (the single app host, serving Razor + `/api/*` + `/mcp`): includes a Node stage to build front-end assets (`npm ci && npm run build` → Vite-hashed output in `wwwroot/dist/`; see `frontend-builder`), then the .NET runtime stage.
- Use `mcr.microsoft.com/dotnet/sdk:10.0` to build and `aspnet:10.0` to run; run as a **non-root** user; expose only the needed port. Set `<ServerGarbageCollection>true</ServerGarbageCollection>` (containers misdetect core count — Workstation GC is wrong for a server process). Add a thorough `.dockerignore` (bin/obj, node_modules, .git, etc.).

### 4. Reverse proxy — HTTPS on loopback
The browser must see HTTPS; the app speaks `h2c` behind the proxy. Add a `caddy` (or YARP) service that terminates TLS and forwards to `web`:
```
# reverse-proxy/Caddyfile
localhost {
    reverse_proxy h2c://web:8080
}
```
Mount the Caddyfile; let Caddy manage its local cert. Don't enable HTTP/3 — it buys nothing on loopback.

### 5. Compose — generate, then split dev vs prod
- Run `aspire publish` to emit `docker-compose.yml` + `.env` from the AppHost (the source of truth). Treat the output as generated.
- Maintain two curated files derived from it:
  - **`compose.dev.yml`** — app + Postgres + Caddy + **full** obs stack (otel-collector, prometheus, loki, tempo, grafana) + Aspire Dashboard.
  - **`compose.prod.yml`** — app + Postgres + Caddy + a **pared-down** OTel Collector writing to a local Prometheus + file logs. **No Grafana/Loki/Tempo, no Aspire Dashboard.**
- Both mirror the AppHost contract exactly:
```yaml
# compose.prod.yml (excerpt)
services:
  postgres:
    image: postgres:17-alpine
    environment: { POSTGRES_DB: kairosdb, POSTGRES_USER: kairos, POSTGRES_PASSWORD: kairos }
    volumes: ["kairos_pgdata:/var/lib/postgresql/data"]
    networks: [kairos]

  web:
    build: { context: ., dockerfile: src/Kairos.Web/Dockerfile }
    environment:
      ConnectionStrings__kairosdb: "Host=postgres;Database=kairosdb;Username=kairos;Password=kairos"
      OTEL_EXPORTER_OTLP_ENDPOINT: "http://otel-collector:4317"
    volumes: ["dpkeys:/keys", "kairos_files:/files"]   # Data Protection keys + attachments
    depends_on: { postgres: { condition: service_healthy } }
    mem_limit: 512m                                     # NFR: steady-state ≤ 300 MB RSS
    networks: [kairos]

  caddy:
    image: caddy:2
    volumes: ["./reverse-proxy/Caddyfile:/etc/caddy/Caddyfile"]
    ports: ["443:443"]
    depends_on: [web]
    networks: [kairos]

  otel-collector:   # minimal pipeline in prod; full fan-out lives in compose.dev.yml
    # see observability-builder

volumes: { kairos_pgdata: {}, dpkeys: {}, kairos_files: {} }
networks: { kairos: {} }
```
- Connection-string env keys use the `ConnectionStrings__<name>` convention so config binding matches the Aspire resource name.
- `depends_on` with `condition: service_healthy` makes dependents wait for *ready*, not just *started*.
- Keep ports, service names, db name, and the OTLP endpoint **identical** to the AppHost contract across both files.

### 6. Launch & verify
- **Dev inner loop:** run `Kairos.AppHost` → the Aspire dashboard shows every resource, logs, and telemetry; service discovery wires web↔db, with MCP served at `/mcp` on web.
- **Full dev stack:** `docker compose -f compose.dev.yml config` (validate) → `... up --build` → confirm web is reachable via HTTPS through Caddy, MCP serves over `/mcp`, Postgres persists, Grafana shows signals.
- **Prod-like:** `docker compose -f compose.prod.yml up --build` → app + Postgres + Caddy + minimal OTel only; no dashboard/Grafana.

### 7. Deployment manifest
`aspire publish` generates the Compose artifact + `.env`; `aspire deploy` launches it **on the local machine** only. Treat the manifest as generated output; keep the AppHost as the source of truth. Deploy by copying the artifact to the target workstation/VM and running plain `docker compose up`.

### 8. Health, startup ordering & migrations
- Expose `/health` and `/alive` from ServiceDefaults; gate compose `depends_on` on `service_healthy` so dependents wait for readiness.
- Migrations apply at startup in **dev** behind an environment guard; for prod prefer an `aspire`/EF **migration bundle** or a one-shot migrator step (see `database-builder`). Never `EnsureCreated()` alongside migrations; don't race app startup against an unready database.

## Conventions

- **One contract, two runtimes.** Resource/service names, ports, the `kairosdb` name, and the OTLP endpoint are identical in the AppHost and both compose files.
- **Dev/prod is a deliberate split.** `compose.dev.yml` = full obs + dashboard; `compose.prod.yml` = minimal OTel-to-disk. The Aspire Dashboard and the Prom/Loki/Tempo/Grafana stack are **dev-only** — guarded by `IsRunMode` in the AppHost and absent from prod compose from the first commit.
- **Every service is containerized** and joins the shared `kairos` network; stateful services use named volumes (`kairos_pgdata`, `dpkeys`, `kairos_files`).
- **HTTPS at the proxy, `h2c` behind it.** The app never terminates TLS itself; no HTTP/3 on loopback.
- **Config via environment**, never baked into images; secrets (OAuth, connection strings) come from the environment/Aspire and are never committed. OAuth tokens are encrypted at rest via Data Protection keys on the `dpkeys` volume.
- **Multi-stage, non-root, minimal** images with Server GC enabled; `.dockerignore` keeps build context lean.
- **AppHost is the source of truth** for the resource graph; `aspire publish` generates compose; deployment is `docker compose up` of that artifact.
- After changes: `dotnet build` clean, `docker compose -f compose.<env>.yml config` valid, both compose files bring up their stacks, AppHost runs the full graph.

## Definition of done

The orchestration layer is complete when: `Kairos.Web` uses `ServiceDefaults`; the Aspire AppHost runs the full resource graph (postgres + web, with MCP served at `/mcp` on web and the dashboard showing telemetry) in dev with dev-only resources guarded by `IsRunMode`; the web service has a multi-stage, non-root, Server-GC Dockerfile; a reverse proxy terminates HTTPS on loopback with the app on `h2c`; `compose.dev.yml` (full obs + dashboard) and `compose.prod.yml` (minimal OTel-to-disk) both come up on one network with persistent `kairos_pgdata`/`dpkeys`/`kairos_files` volumes; names/ports/db/OTLP endpoint match across AppHost and both compose files; `aspire publish` regenerates the Compose artifact; and health checks gate startup ordering. Anything skipped is called out explicitly.
